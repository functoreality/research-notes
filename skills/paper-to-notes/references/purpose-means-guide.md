# 目的手段链条 —— 详细方法论

> 本文件是 SKILL.md 中「分析框架」的详细补充。初次分析论文时不需要通读。当遇到以下情况时查阅：
> - 无法判断某个技术要素应归属到目的手段链的哪一层
> - 需要确认展开是否足够完备（是否跳步）
> - 需要区分「实然因果拆分」和「开放系统提方案」两种展开方式
>
> 本方法论根植于现代 TRIZ 理论，详细笔记见 `perspective/triz.md`（`{p9ml8p}`）。

## 一、目的手段链条 vs 因果链分析

这是两套不同场景的分析工具（`perspective/triz.md` `{p3af04}`）：

| | 目的手段链条 | 因果链分析 |
|---|---|---|
| **适用场景** | 解决方案生成（系统设计）——需要实现一个新功能 | 判别器分解（问题分析）——已有方案有明显缺点需消除 |
| **因果关系类型** | 目的因（为了实现 X，需要 Y） | 动力因（发生 A 是因为发生了 B） |
| **展开宽度** | 宽，开放——涉及引入外部资源、机制 | 窄，封闭——只考虑特定系统内的情况 |

在论文分析中：
- 论文的「我们提出了什么新方法」→ 用目的手段链条分析（该方法服务于什么目的？分解为什么子问题？）
- 论文的「旧方法有什么问题」→ 这部分用因果链分析，但通常只需理解、不需要纳入笔记（除非该问题分析本身有迁移价值）

## 二、节点类型体系

目的手段链条区分三种节点（`perspective/triz.md` `{p9ml8p}`）：

### 2.1 属性状态

「使现有对象或系统产生新行为」。表述为系统需要达到的状态或性质。

- 展开方式偏**实然因果拆分**（封闭系统推演）：「手段—导致它的属性因素」
  - 各节点是静态性质，无时间先后
  - 例：映射准确 → (训练集上准确, 泛化能力)
- 也可以按**开放系统提方案**展开为科学效应或新对象（见下）

### 2.2 科学效应（手段大类）

输入输出变换，抽象大类下有多种具体方案——**OR 关系**。

- 例：「使船体附着物变弱」← (OR: 机械, 电, 热, 声, …)
- 在笔记中，同一层级应列出尽可能多的方案大类（保证宽度）
- 论文提出的具体方案是其中一个分支

### 2.3 带性质的新对象（手段细化）

「产出具有某性质的对象」——将原问题转化为产生新对象的问题。对象的子结构之间是 **AND 关系**。

- 例：「支撑物体」← 「柱体, 性质=硬」
  - 柱体的子结构（材料、形状等）是 AND 关系，缺一不可
- 子手段展开可能是动态拆解（有时间顺序）：目标状态 → 中间状态 → 原始状态

### 2.4 跨阶段继承

设一阶段有 A ← B（因果关系），二阶段有 C ← D（方案细化）。则跨阶段 B ← D 意味着 A ← D、B ← C、A ← C 也成立。

实用含义：如果一条粗糙手段链形如 A ← C，可以设法细化为 B ← D。细化后不仅能看出原假设服务于什么因素，还能进一步提出新方案。

## 三、展开原则

### 3.1 避免跳步

每层尽量拆充要条件（`perspective/triz.md` L73-75）。不要从顶层目的直接跳到具体手段。

**坏例子**：「如何实现跨材料泛化」→「用 ICM」
**好例子**：「如何实现跨材料泛化」
→ 「如何让网络适应不同材料的本构关系？」
→ 子问题1：「本构关系如何表示为网络可处理的形式？」→ 方案：方程系数作系统表示（OR: 直接输入材料参数 / 隐向量编码 / …）
→ 子问题2：「网络输出应该是什么？」→ 方案：能量密度梯度（OR: 直接输出应力 / …）
→ 子问题3：「如何训练？」→ 方案：方程残差作 loss（OR: 模拟数据监督 / …）

### 3.2 保证宽度

同一层级列出尽可能多的方案大类（OR 关系）。不只记录论文所用的那一种。

这保证了笔记不只是「这篇论文做了什么」的记录，而是「对于这个子问题，目前已知有哪些方案大类」的知识库。

### 3.3 区分 AND 和 OR

- **OR**（方案选择）：科学效应层级的展开。不同大类之间是替代关系。
- **AND**（必要条件）：对象组件层级的展开。各子结构必须同时存在。

同一层级可能混合 AND 和 OR。例如 `aisc1.md` 中上下文方案的三个要素（系统表示 AND 映射表示 AND 训练），而每个要素内部又有 OR 分支（如训练 loss 可基于系统响应 OR 基于局部方程）。

## 四、已有目的的新手段 vs 已有手段的新目的

这是判断笔记补充位置的**最核心决策**。

### 判断流程

1. 识别论文中该技术要素所服务的**目的**（顶层属性状态）
2. 搜索笔记：是否有以该目的为组织维度的框架？
3. 识别该技术要素所使用的**手段**（数学对象、算法类型）
4. 搜索笔记：该手段是否已被记录？被记录在什么目的分类下？

| 目的 | 手段 | 判断 | 操作 |
|---|---|---|---|
| 笔记已有 | 笔记已有 | 非新颖 | 不记录（或仅文献笔记） |
| 笔记已有 | **新** | 已有目的的新手段 | 在该目的下的手段分支添加 |
| **新** | 笔记已有 | 已有手段的新目的 | 在目的分类下创建新范畴 |
| **新** | 新 | 全新的贡献 | 同时创建目的范畴和手段条目 |

### 案例

ICM 论文的「方程系数作网络输入」：
- 目的：将目标物理系统表示为网络可处理的形式（→ 笔记中此目的尚无独立框架）
- 手段：PDE 残差 / 离散方程系数（→ 笔记中此手段记录在 `{n3bg3i}` 下，但仅作为「评判解/方程质量」的手段）
- 判断：**已有手段的新目的**
- 操作：在 `{n3bg3i}` 下创建新范畴「非评判目的：作系统描述」

如果误判为「已有目的的新手段」，就可能在 `NOarch.md` 的 token 化条目下添加——这是错误的归属位置，因为手段虽涉及 token 化，但本质创新在于目的而非手段。

## 五、分析时的常见陷阱

### 5.1 混淆手段和目的的分类

笔记中同一个手段可能出现在多个目的分类下。例如 PDE 残差既出现在「评判解的质量」下（传统 PINN loss），也出现在「评判方程的正确性」下（系统识别），还在 ICM 后新增了「系统描述」用途。

分析时不要看到「这个手段笔记已有」就认为覆盖了——必须确认「服务于同一目的」才算覆盖。

### 5.2 把方案设想当作权威框架

笔记中有部分内容是思想不成熟阶段的方案设想（如 `largeNN.md` 的废弃节），组织松散，不应作为新内容的归属地。优先寻找系统分析层的框架。

### 5.3 以论文为单元而非要素为单元

一篇论文通常包含 3~8 个独立的技术要素，各自可能需要归入不同的笔记框架。不要把论文作为一个整体来评估。

### 5.4 过度关注实现细节

论文的网络架构细节、超参数选择等通常不满足非平凡性（标准组件的显然组合），不需要迁移到主笔记。文献笔记中记录即可。
