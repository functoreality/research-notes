# 迁移与完整性

## 1. 建立来源去向记录

在工作记忆、临时文件或任务计划中，为每个待处理信息点记录：

```text
来源文件和稳定位置 | 原信息点 | 处理方式 | 目标位置 | 改写原因 | UID 与链接处理
```

处理方式包括：

- 迁入：知识所有权转移到新位置，源端共享正文删除
- 留存：内容依赖原场景或不属于目标框架
- 合并：与目标位置已有判断语义等价，说明合并后的承载位置
- 删除：只有确属重复、过时或用户已授权删除时使用，并说明依据
- 暂缓：存在范围、语义或用户决策问题，原内容保持不动

去向记录既用于每批自检，也用于中期和最终审查。

## 2. 选择迁移块

优先选择能独立成立的语义子树或一组紧密相关的信息点。
来源不必连续，同一源块迁入后也可分散到多个目标位置。

批次大小由以下因素决定：

- 能否完整保留一个语义块
- 是否只触及目标框架的少数分支
- 用户能否有效审阅
- 审查者能否追踪来源去向

不设置固定 bullet 数量。新增接口、反向链接或导航说明不计为实质迁移。

## 3. 默认保留成熟正文

重构首先改变结构，不自动授权重写正文。

来源优先级为：用户最新修改、成熟主笔记、文献笔记、执行者现场重述。
文献笔记用于核对证据，不应用来覆盖已经完成跨语境翻译的主笔记表达。

迁入前为每个信息点判断：

- 原文保留：只调整缩进、排列、必要链接和最少指代
- 必须改写：记录原文依赖旧语境、存在歧义、不准确或不完整的具体原因

改写时逐项保护：

- 对象和动作
- 抽象层次
- 判断力度和不确定性
- 适用条件
- 公式和数学关系
- 来源证据和相关链接
- 原有信息密度

无法确定新表述是否更好时保留原文。评审提出可读性意见不自动授权重写，
先判断问题是否由本轮结构造成，以及改写是否损失成熟抽象。

## 4. 重建目标语境

按目标父节点和邻近内容调整迁入节点：

- 原文依赖旧父节点背景而新位置没有时，补足最少背景
- 原文重复了新父节点已经提供的背景时，删除重复
- 改用目标框架已经定义的对象、术语和关系
- 调整信息顺序，使其符合新框架的阅读路径
- 一个 bullet 表达完整判断，子节点不续写父节点未完的句子

跨语境翻译只解决新位置无法独立成立的问题，不是每次迁移都重新解释正文。

## 5. 映射技术对象和数学记号

保留公式前，列清源、目标符号各自表示的：

- 对象
- 定义域和值域
- 离散或连续性质
- 在当前框架中的角色

只有语义对象等价时才统一记号，公式和邻近文字需同步修改。
找不到同类型、同含义的目标对象时，停止迁移该点，重新检查它是否属于目标框架。

不要把 PDE 残差与 PDE 解的残差、离散分类输出与连续调制量等
表面相似但语义不同的对象互换。

## 6. 处理一般方法、实例和证据

源块同时含一般方法与论文实例时：

1. 将一般操作、判断或公式放入目标框架的相应方法节点
2. 将论文实例挂在它采用的方法下面
3. 实现细节通常留在文献笔记，通过文献 UID 到达
4. 实例中发现的可复用策略应提升为一般知识，实例另作叶节点

一个文献 UID 只支撑其锚定位置实际陈述的判断。
一个节点包含多个可独立验证的判断时，拆分节点或分别配置证据。
详细 UID 和链接规则服从 Main Note Integration。

### 6.1 迁移既有 UID 与遗留链接

- 遇到旧式链接，先定位其真实目标，判断它原本支撑、指代或导航的内容，
  再转换为当前链接形式，不只替换语法。
- 一个源信息点拆成多个判断时，原文献 UID 移到仍由它支撑的判断；
  其他判断分别寻找证据或新增 UID，不能用更精确的新链接无意替代旧判断。
- UID 移动后，检索全部引用位置。除确认解析有效外，还要更新已过时的
  路径、角色和接口说明。

## 7. 写入、核验和删除顺序

对每个迁移块按以下顺序执行：

1. 记录来源稳定位置和完整父子范围
2. 写入目标位置并按新语境调整
3. 核对文字、公式、UID、链接和 Tab 层级
4. 对照源块逐项确认目标或留存位置
5. 删除源端已经迁出的共享正文
6. 再次检查原框架是否仍语义完整

删除源父节点前，枚举它的所有直接子节点。只有子节点均已迁出、删除，
或明确重挂到合理父节点后，才能删除父节点。

否则剩余子节点会悄然改挂到上一个同层节点，破坏原框架含义。

单框架重组同样遵循先建立新位置、再移除旧位置的顺序。
若新旧位置位于同一文件，分小步编辑并在每步后检查缩进结构。

## 8. 判断一块迁移是否完成

完成需要同时满足：

- 目标位置接收了源块的实质判断、公式、方案或实例
- 源端不再保留应由新位置拥有的正文副本
- 场景特有内容仍留在原框架，并能独立理解
- UID 随其锚定的实质内容移动，没有复制定义
- 迁移和留存内容合计没有信息丢失

只增加链接、接口或概括不算迁移完成。

## 9. 导航与链接收尾

正文迁移基本完成后再统一检查导航。最低目标是读者从原框架的根节点或
主要入口出发，能通过直接链接或一层内无歧义的入口发现新框架。

同一知识服务多个问题时：

- 详细解释保留在主要位置
- 其他位置按当地问题写简短入口
- 不原样复制正文让读者猜用途
- 必要时建立反向链接，使两个方向都能发现重构后的知识位置

链接角色、空格、作用域、实例标记和 UID 标点服从 Main Note Integration。
裸名称不足以辨认目标时，用短横线连接最短必要的祖先路径补充标签；
只保留帮助读者定位主题的层级，不机械抄写完整路径。

## 10. 使用 Git diff、grep 和语义复核

有明确历史基线时，记录 commit 哈希并显式比较基线到当前状态。
不要依赖默认工作树 diff 猜测重构的完整范围。

Git diff 可用于枚举删除、改写和移动的文本，grep 可用于搜索 UID、术语和
可能对应位置。它们只提供证据，不替代语义判断。

以下情况必须人工语义复核：

- 内容经过压缩或重新表述，关键词不再相同
- 一个旧节点拆到多个目标位置
- 多个旧节点合并为一个一般判断
- 相同术语在不同框架中含义不同
- 没有可靠 Git 基线

没有 Git 历史时，使用来源去向记录和迁移前保存的明确来源清单完成核验。

## 11. 用户修改和范围外内容

文件内容与此前读取不一致时，视为用户可能已经修改。
重新理解当前文本，不自动恢复旧版本。

只修复本次迁移直接造成的失效链接、错挂和语境问题。
范围外的相邻问题记录后交给用户，不顺手重构。
