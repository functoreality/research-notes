## 任务目标

给定一篇论文，判断它对本笔记系统是否有值得补充的新信息。核心问题不是「笔记有没有讨论过这个主题」，而是：

> 论文的各个技术要素分别解决了什么（子）问题？笔记中是否有以该（子）问题为组织维度的框架？如果有，该要素作为该问题的一种新手段是否值得记录？

输出是一个简洁报告，重点在「可补充什么、补到哪里、为什么」。

## 工具准备

**开始前，必须先阅读 `../outline-read/SKILL.md`**（`outline-read` skill），了解 outline-read 工具的完整用法。后续不再重复这些基础用法。

### 文章来源获取

- arXiv 论文优先看 HTML 版。WebFetch 会截断固定长度，若不完整可下载到本地后读（可结合 `html2text -nobs`、`pdftotext`）
- 对已有论文的解读报道，应自行找原论文阅读，以原文为准

从 arxiv.org 下载常遇 QoS 限速，速度衰减到 0，增大超时无用。建议下载命令：

```bash
wget -c --tries=20 --timeout=30 --waitretry=5 --read-timeout=20 -O 目标文件名 URL
```

优先下 HTML；PDF 较大可能触发多次重试。备选 curl 手动续传：

```bash
curl -L -C - --max-time 60 -o 目标文件名 URL
# 反复执行直到 wc -c 等于 HEAD 查到的 content-length
# 出现 0 字节响应是冷却期，隔几秒再试
```

## 分析框架：目的手段链条

这是评估一篇论文的**核心思维工具**。不要问「笔记有没有讨论过 X 主题」，而要按以下方式思考：

### 根本逻辑

笔记的顶层组织维度是「某个数学对象/技术手段被用来解决**什么问题**」，而非「这个手段本身是**什么类型**」。因此分析一篇论文时：

1. 将论文拆解为多个独立的技术要素（通常 3~8 个）
2. 对每个要素，追溯它解决了什么（子）问题
3. 在笔记中找到（或发现缺失）以该（子）问题为组织维度的框架
4. 判断该要素是「已有目的的新手段」还是「已有手段的新目的」

### 「已有目的的新手段」vs「已有手段的新目的」

这是最关键的一步区分：

- **已有目的的新手段**：该要素服务于笔记中已识别的某个目的，但使用了一种新的手段。记录时归入该目的下的手段分支。
- **已有手段的新目的**：该要素使用了一个笔记中已知的手段，但服务于一个**新的目的**。记录时不应在手段分类下添加条目，而应在目的分类下创建新范畴。

**案例**：ICM 论文的「方程系数作网络输入」。
表面上看是关于 token 化的（手段分类，`NOarch.md`），但实质是 PDE 残差被用于了新目的——「系统表示」而非「评判质量」。
因此在笔记中，这一要素被记录在 `PINN.md` 的 PDE 残差条目下（新增「非评判目的：作系统描述」范畴），而非 `NOarch.md`。

### 链条展开原则

展开目的手段链时：
- **避免跳步**：每层拆充要条件，不要从顶层目的直接跳到具体手段。
  一般模式：顶层目的 ← 识别 2~4 个子问题← 每个子问题再各自展开方案大类。
  例如「构建 目标系统→s→r 的映射」不应直接跳到「用 ICM」，而应先拆为「目标系统如何表示为网络输入」「映射如何表示」「如何训练」三个子问题，再在每个子问题下列出方案。
- **多用公式**：遇到可量化的子问题时，先找出其定义/计算公式，将公式中的每一项作为独立分支展开。公式是避免遗漏因素的强大手段。
  例如 ICM 论文中，离散化平衡方程 ∑A∇ψ(I)=0 就是将「本构关系表示」拆解为 A（系数矩阵）和 I（应变不变量）两个独立要素的公式依据。
- **保证宽度**：在同一层级列出尽可能多的方案大类（OR 关系），而非只记录论文所用的那一种。
- **区分节点类型**：属性状态（期望达成的结果）、科学效应（手段大类，OR 关系）、带性质的新对象（手段细化，子结构 AND 关系）。
- **节点表述必须为动宾短语**：链条中每个节点的表述必须是「动词 + 宾语」的形式，必要时可加入：
  - 定语（修饰宾语），如「学习算子分裂的调度策略」中「调度策略」是宾语，「算子分裂的」是定语
  - 状语（描述达成方式），如「基于 ES 优化来训练小型策略网络」中「基于 ES 优化」是方式状语
  - 属性状态（期望达成的结果）也按动宾短语表述，如「获得 OOD 下稳定的 PDE 代理」而非「OOD 鲁棒性」
  - 禁止使用名词短语（如「OOD 鲁棒性」「模块化」「可解释性」）直接作为节点——这些是分类标签，不是目的手段链中的环节
- **节点之间用 `←` 连接**：链条写作 `A ← B ← C`。
  - 箭头右侧节点是实现左侧节点的手段（「B 实现了以后可以使 A 实现」）
  - 禁止混入其他关系：
    - 时间顺序（先做 B 再做 C）
    - 工作流步骤（如 compose → diagnose → enrich）
    - 单纯的因果链（A 导致 B）
  - 检验方式：读出每一段 `←`，问「右侧手段的达成，是否直接构成为实现左侧目的提供了可能？」答案若否，则该段不是目的手段关系

> **重要**：目的手段链的分析必须独立完成，不能照抄笔记中已有的表述。笔记中的内容未必符合动宾短语规范，若照抄会导致链条形式不合格。应从论文出发、独立构建符合规范的链条，再将笔记中的框架映射到该链条上。

更详细的目的手段链条方法论（节点类型、AND/OR 区分、属性状态展开方式等）见 `references/purpose-means-guide.md`。通常不需要在初次分析时通读，但在遇到以下情况时查阅：
- 无法判断某个要素应归属到链条的哪一层
- 需要确认展开是否足够完备（避免跳步）
- 需要区分「实然因果拆分」和「开放系统提方案」两种展开方式

## 探索流程

### 入口选择

1. **`keywd.md`**：全量读取或搜索关键词（中英文各搜一次），得到相关 `((UID))`。
2. **主笔记文件名匹配**：根据论文主题选择可能相关的主笔记文件，用 outline-read 浏览目录。
3. **全局搜索**：在所有笔记中搜索可能相关的关键词。同一概念建议中英文各搜一次；一种语言搜不到就换另一种。使用当前环境可用的搜索工具，不必拘泥于特定命令。

搜索范围不限于论文主题相关的领域框架；额外检视一般 ML 框架中是否有可容纳本要素的条目——领域要素可能是一般概念的实例化（如物理诊断选 checkpoint 是 early-stop 的 PDE 版本），主题关键词搜索容易遗漏这种映射。

### 深入探索：UID 链跳转

找到相关关键词或 `((UID))` 引用后，**必须**用 outline-read `--uid` 跟随链接链。

典型流程：`keywd.md` 找到关键词和 UID → `outline-read --uid` 跨文件跳转 → `read` 看周围原文 → 发现新 `((UID))` 引用 → 继续跳转 → 重复。

**不要只看搜索的碎片命中**。沿 UID 链跳转才能理解笔记中的完整讨论和上下文关系。

### 选择新内容加入位点

- 若在文献笔记中发现与新论文高度相关的内容，需注意已有文献笔记不能作为新内容插入的位点
  - 应反向追踪该文献笔记条目的 `{_UID}` 到主笔记中引用它的 `((_UID))` 处，该引用附近才是允许的插入位点；如果需要，可沿主笔记结构进一步选更合适位点
  - 注意这与探索阶段的跳转方向相反：探索可能从主笔记去文献笔记看细节，通过正向链接跳转；选位点是从文献笔记回到主笔记，通过反向链接搜索
- 引用笔记内容时，优先使用 UID（如 `{n3bg3i}`）而非行号。行号随笔记编辑频繁变动，UID 基本稳定

## 评判标准与迁移筛选

笔记用户是 PDE 基础模型（计算图编码 PDE 路线）的通用算法研究者，不是特定应用的使用者。
对架构和算法，无通用启发则不记。
对数据集，用户需要尽可能搜集公开可用的数据（用于预训练混入或 benchmark 比较，二者满足其一即可），判断标准为「是否公开可用且与笔记领域相关」。

### 两阶段筛选

**阶段一：技术要素是否有价值？**

分析每个技术要素的目的手段链，判断其在笔记框架中的位置。满足以下任一条件则有继续评估的价值：
- 论文的技术要素对应笔记中某个框架的**缺失环节**（该框架下有这个子问题但尚无此手段）
- 论文使用了一个已知手段但服务于**新的目的**（需扩展目的分类）
- 论文的技术要素与笔记中已有的结论形成**有趣对照**（如笔记认为 scaling law 对 AI4Sci 不适用，论文提供了反例）

**阶段二：是否迁移到主笔记？**

即使有价值，也需通过三要素筛选才进入主笔记。类似专利授权标准：

| 标准 | 含义 | 检验方式 |
|------|------|---------|
| **新颖性** | 主笔记现有框架中不包含类似做法 | 沿目的手段链逐层检查：该层是否已有此方案大类的记录？ |
| **实用性** | 不限于当前问题，可迁移到更一般框架 | 向上抽象一级：去掉当前问题的特定条件后，该手段还能用于什么场景？ |
| **非平凡性** | 不是标准组件的显然组合 | 问：如果已知该层的目的和可用资源，一个合格的研究者是否能自然想到这个手段？如果不能，则非平凡 |

**优先级映射**：
- **高**：通过三要素筛选，建议迁移到主笔记，且现有框架有明确的归属位置
- **中**：通过三要素中的两条（如新颖+实用，但非平凡性存疑），或者有价值但需先扩展框架才能归入
- **低**：仅通过阶段一（有价值），但不满足三要素；或仅作为有趣对照，不需要迁移

**不满足三要素的内容**：保留在文献笔记层（`AISClitN.md`），仅服务于「重新看这篇论文时知道它在干什么」的需求。

**关于文献笔记→主笔记的同步**：不存在强制约定。只有通过三要素筛选的要素才需要同步。具体实现细节（如特定的网络架构组合、超参数选择等）通常不满足非平凡性，留在文献笔记即可。

若值得迁移，**迁移位点仅限主笔记**：即便某个文献笔记条目与新论文高度相关，也不应将文献笔记本身列为迁移目标，而应追踪该条目 UID 到主笔记中的引用位置。

### 一般框架 vs 领域框架的位点选择

当同一要素在领域特化框架和一般框架下都有候选位点时，优先评估一般框架的适用性。
若该要素是一般 ML 概念的领域实例化、对非该领域的读者也有参照价值，以一般框架为主版本，加领域标签标注身份即可。
例如，early-stop 下「物理诊断选 checkpoint」本身针对 PDE 场景，但可启发其他场景根据领域指标选 early-stop 时机，记入一般框架。
若要素纯属领域特化、对一般框架无迁移启发，仍放领域框架。

### 框架适配性检查

将新要素归入现有框架时，如果感到别扭——新要素横跨多个现有类别、无法干净归入其一，或现有层级结构中找不到合适的节点——可能意味着框架本身的**组织维度**需要调整，而不仅是内容缺失。

检验方式：框架当前按什么维度分类（如「判断力来源」「手段类型」）？这个维度是否抓住了问题的**根本目的**？如果框架按「手段来源」组织，而新要素更适合按「目的」分类，就说明组织维度有改进空间。

注意与「已有手段的新目的」区分：
- **新目的**：在现有框架的顶层扩充分支（如 PINN 残差下新增「非评判目的」范畴），框架的组织维度不变
- **框架重构**：改变框架本身的分类维度（如从「按判断力来源」改为「按根本目的：匹配 / 优化 / 约束」），是更高层级的调整

建议原则：
- 可以提，门槛不必高——用户会自己判断是否采纳
- 对各个重构建议给出优先级评估，尤其当建议重构的框架数量较多时
- 优先提那些「替代维度明显更优」的，而非模棱两可的微调

### 主笔记位点的概念精度

选择「建议加入」的主笔记位点时，必须对相关概念之间的细微差异保持敏感。

常见易混淆概念（仅示例，实际分析中应保持警惕）：

- **PDE 残差** vs **PDE 解的残差**：
  - 前者（$r = \mathcal{L}u - f$）是方程不满足程度的局部度量，用于 PINN loss 设计；
  - 后者（$\|u - u^*\|$）是解逼近真解的全局误差，用于评估模型精度。两者用途完全不同。
- **Loss** vs **Error**：
  - Loss 用于训练中的梯度反传，训练完成后不再关心；
  - Error 用于评估最终网络表现，不参与反传。
  - 两者服务于不同的分析框架：Loss 是优化手段，Error 是质量评判标准。

在推荐位点前，必须：
1. 确认论文要素所属的**概念类型**（训练手段还是评估方法？作用在时间维度还是空间维度？）
2. 确认目标框架的**组织维度**（该框架按什么分类？手段来源、问题类型、还是作用对象？）
3. 只有当概念类型与框架的组织维度匹配时，才建议该位置

如果找不到概念上精确匹配的框架，宁可承认「当前笔记缺少以此维度组织的框架」（可建议新建），也不要强行归入一个表面相关但实质不同的条目下。

### 关于框架成熟度

笔记中不同部分的框架成熟度不同。探索时注意区分：
- **方案设想层**（如旧 `largeNN.md` 的废弃节）：枚举可能的技术路线，组织松散，偏发散探索。**不应作为新内容的首选归属地。**
- **系统分析层**（如 `PINN.md` 的 PDE 残差条目、`aisc1.md` 的本构关系学习条目）：聚焦核心问题，按目的手段链展开，偏收敛分析。**优先将新内容归入此类框架。**

### 关于数据集

**输出报告前必须完成所有验证，报告中不得出现「需验证」「待确认」等字眼。**

数据集状态的完整判断流程（五种基本情况、搜索策略、两个独立验证维度、报告要求、记录位置）见 `references/dataset-guide.md`。以下为关键原则摘要：

- 五类基本情况：A 不涉及 / B 全用现成 / C 自建但未搜到 / D 未提及但搜到 / E 论文提及
- 对 D 和 E，必须实际访问公开位置，独立验证两个维度：**(1) 是否包含可直接获取的数据集文件**（注意：仓库内可能只有外部下载链接而非 git 管理的数据）、**(2) 是否包含数据生成代码**。两个维度独立判断，互不排斥
- 搜索时优先 Google，不可用时换 Bing；同时搜索 GitHub 和 Hugging Face；中国大陆网络环境下可尝试镜像站（`bgithub.xyz`、`hf-mirror.com`）
- 笔记中数据集主要记录在 `numeric.md`，条目分散（如有些在各方程类型的对应位置）。找入口：文件内搜「数据集」，命中后沿周围层级结构定位到合适的子节。浏览建议用 outline-read。
