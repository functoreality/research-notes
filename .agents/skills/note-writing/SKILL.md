# 文献笔记写作指南

> 本 skill 关注笔记的**思想质量**：如何阅读、如何思考、如何组织、如何压缩。
> 关于**格式验证**，写完后运行本 skill 目录下的 `scripts/check-note.sh "$FILE"`。

## 1. 笔记的本质

你是一个领域专家，在给自己写速记笔记。你的笔记是你消化后的理解和评判，是你与论文的对话记录，不是论文的缩略版。

**你在思考，不是在摘录。** 你不是在忠实记录论文的论述，而是在从论文中提取对你最有价值的部分，形成你自己的判断。
你的笔记里应该有论文没有的东西：你的质疑、你的重新框定、你的抽象和联想。
如果论文对问题的诊断和你的理解不一致，写下来。如果某个方法让你想到另一个领域的类似做法，写下来。
这些对话才是笔记的价值所在。

具体落实到三个思考动作：

1. **追溯因果链**：追问"为什么会有这个问题？""这个方法的本质是什么？""它为什么能起作用？"把你的理解写下来。
2. **形成判断**：这个方法是否优雅？实验是否充分？有什么局限？把你的判断写下来。
3. **压缩本质**：只保留最核心的洞察。读者（未来的你）已有领域知识，不需要基础概念解释或背景铺垫。

**深度由论文对你的价值决定，不由论文的长度决定。** 有些论文三五行核心洞察就够，有些值得展开几十行。不要每篇都写成同等深度。

**笔记质量和篇幅无关。** 一句话的精准判断胜过一百句话的泛泛摘录。
不断添加细节往往使笔记变差而非变好，每增加一行都要问：删掉它会影响我理解核心洞察吗？如果不会，就不写。
每写完一部分，问自己：这段内容是否在帮助理解核心洞察？如果不是，删掉。

**在提出批评之前，核实事实依据。** 如果你想指出"论文只测试了 X"或"没做 Y 消融"，确保你确实在论文中查证过。基于错误事实的批评比不批评更糟糕。

## 2. 阅读与组织

### 2.1 阅读阶段：带着问题读

**读完整论文，不要依赖二手摘要。** 如果 Web Fetch 截断了网页内容，用 curl 下载文字版或 PDF 到本地再读取。

读论文时不要被动接收信息，而是在脑中主动回答三个问题：

1. **这篇论文最根本的问题是什么？** 它在诊断什么现象？（不是论文声称要解决什么，而是它实际解释了什么问题）
2. **论文解决这个问题的手段中，哪个设计选择最关键？** 哪个选择如果换掉，整个方法就垮了？
3. **我有什么不同意、不确信、或者想追问的？** 找到一个你最想质疑的点，在阅读中积累证据。

**思考深度必须远超作者。** 不要满足于理解作者说了什么。更进一步：试着把作者说的内容用你自己的概念框架重写。
比如，作者叫它 "constraint-aligned optimization"，你可以写成 "ansatz 设计"，同一个方法，完全不同的解读角度。
笔记不应局限于记录作者的表述。如果可行并且有价值，完全可以换一个框架重新讲这个故事。
你的笔记应该有作者自己想不到、写不出来的内容。

读完论文后，用一句话回答：**如果一年后回来看这篇笔记，我最可能因为什么原因回来查？** 这句话决定了你笔记的核心洞察应该放在哪个层次。

### 2.2 找到核心洞察

读完论文后，先问自己：**这篇论文如果只用一句话告诉别人，我会说什么？** 那句话就是你的核心洞察。整篇笔记的组织都围绕它展开。

**核心洞察有时不是论文自己声称的贡献，而是你从中发现的微妙之处**，某个关键的设计选择、一个非平凡的技术取舍、一个解释了"为什么方法有效"的深层数学结构。
捕捉这些"聪明之处"，它们比论文的自我总结更有价值。

**选择正确的抽象层次。** 核心洞察不是论文里最深奥的那个定理，也不是最笼统的那个概括。它应该处于"能解释现象"的层次，而非"能推导一切"的层次。
一个好的测试：如果一年后你回来查这篇笔记，你最容易忘记的是什么？定理的形式化表述可以回头查论文，但定理揭示的现象机制（它如何解释你关心的那个问题）才是你不会想到去查、但笔记里最需要的。具体来说：

- 一篇理论分析论文，核心洞察往往不是最顶层的定理陈述，而是定理揭示的因果链：现象→机制→后果。把定理本身作为支撑证据即可，不必作为组织骨架。
- 一篇方法论文，核心洞察往往不是"用了什么模块"，而是设计选择背后的约束和权衡：为什么这样设计而不是那样。

不同类型的论文，核心洞察的展开方式不同：

- **理论洞察型**（论文的核心贡献是一个新的理论发现，如某个定理揭示了问题的几何根源）：从理论发现出发，推导出它如何解释现象、如何引出方法，最后评价这个理论的解释力有什么局限。
- **实验发现型**（论文的核心贡献是对一个广泛使用的方法进行了系统的实验检验，发现它在某些条件下失效）：从发现出发，拆解失效机制，再讨论论文提出的修复方案是否足够。
- **方法设计型**（论文的核心贡献是一个新的架构/算法/训练策略）：从方法的设计原则出发，展开它为什么这样设计、和已有方法的关系是什么，再评价设计的优雅性和局限。
  - 适合用目的手段链展开（顶层目的 ← 子问题分解 ← 各层手段）
    - 注意这指的是设计笔记逻辑结构时的分析方式，最终笔记格式未必用“←”
    - 对于其他形态的展开逻辑（如步骤先后顺序），仅在明显更清晰、更方便未来设计其他系统时参考的前提下，才考虑换用
  - 目的手段链在文献笔记中的常用表示方式举例（不枚举），请选用逻辑关系呈现最清晰的方式：
    - 多个同级 bullet 的排列顺序（目的在前、手段在后）
    - 父子 bullet 的缩进层级（父节点目的、子节点手段）
      - 尤其适用于手段有多个的情形（比如 or 关系的多种方案，and 关系的多个要素），每个作为独立子节点
    - 单个 bullet 内各信息点的排列顺序，其中少数情况（若确实更清晰）可沿用“←”标记
  - 常见展开维度：
    - 形态：（任务/网络/子模块/…的）输入输出形式；若输入、输出复杂则各自成行、分别讨论
    - 推理：部署时如何使用，总输入经何运算产生总输出，各阶段输入输出与职责划分
    - 训练：如何训练使推理可行，训练顺序、各阶段目标、支撑推理的关键约束
    - 各维度独立判断是否值得写，值得写则分开成行，不值得则省略
    - 各维度内部也可进一步再展开手段链
  - 记录具体做法（如 loss 公式、训练步骤）时，可先解释其合理性、依据的原理
    - 例：某 loss 设计依据可能是“二网络分别预测 X 的结果应一致”，最终 loss 的具体形式只是实现该目的的一种手段
    - 理由：完善目的手段链，避免跳步；原文逻辑可能只说“目的A ← 手段B”，这里实际上是要求根据自主分析补成“目的A ← 手段所用原理C ← 具体手段B”
    - 论文未给出时可 `（AI 评）` 补自己的理解
- **质疑驱动型**（你读完后发现论文对问题的诊断可能不对，或者方法和声称之间有差距）：从你的质疑出发，用论文中的内容来佐证你的质疑，同时也要诚实地呈现论文做得好的地方。

**不要把所有论文都套进同一个"问题→原因→方法→实验→评价"的模板。** 这个模板是论文自己的结构，不是你思考的结构。

### 2.3 围绕核心洞察组织

确定了核心洞察之后，笔记中的每一个内容块都应该服务于它：解释它、支持它、细化它、或者挑战它。如果一个内容与核心洞察无关，跳过它。

常见的情况：
- 如果论文的理论部分是你觉得最有价值的东西，方法细节和实验可以压缩到一两行，甚至完全不写。
- 如果论文的实验设计特别精巧、数据构造方式值得学习，那就把实验和数据展开，理论部分一笔带过。
- 如果论文的某个章节让你产生了实质性的质疑，你的质疑本身就是笔记的主线，其他内容都围绕它组织。

## 3. 撰写笔记

### 3.1 写入位置

- **新建笔记**：先写入临时文件，不要直接写入笔记系统正式文件（`raw/AISClitN.md` 等）。后续由调用方工作流决定并入哪个正式文件。
- **编辑已有笔记**：直接写入正式文件。

### 3.2 信息排列原则：先场景，再目的，后手段

无论哪一层（TLDR、骨架 bullet、子 bullet），信息顺序一律按「场景/问题 → 目的/目标 → 手段/方法」排列，对应查阅时的自然追问：

> 在什么场景下遇到什么问题 → 想达到什么效果 → 该用什么方法

三层不必全部出现。只出现两层时保证顺序不变即可；只出现一层则无所谓顺序。

例："交叉验证法：推理时决定是否启用变换"不对，改成"推理时决定是否启用变换：交叉验证法"
（"推理时"=场景，"决定是否启用变换"=目的，"交叉验证法"=手段）

场景描述依据的是方法能处理的范围，请通过自主分析确定。它可能大于或小于作者声称的范围、实验测试覆盖的范围。

场景通常只描述使问题出现的设定，不描述假定可使用的资源。
- 反例：未知方程求解，"若有短轨迹可用"不属于这里所说的"场景"，因为"短轨迹"是方法所利用的资源
- 理由：资源是使方法可行的支撑，应视为方法的再下一层手段，留到方法描述后才讨论
- 例外：该方法假定的可用资源相当不常见，并且预判未来读者带着问题回来查时，前置的资源声明最有助于读者判断其后内容是否有用、值得细看

### 3.3 骨架与 TLDR 设计

#### TLDR

写 TLDR 之前，先推演一年后你遇到什么问题时，会想起这篇论文，回来查这份笔记。
把问题写下来（草稿，不写入笔记），然后 TLDR 直接回答它。

例：
- 原文要点：冻结 ICON 外挂闭式算子链，把 OOD 目标重构回模型可靠 regime
- 推演问题：ICON 遇到预训没见过的算子怎么办？要微调吗？
- 笔记 TLDR：ICON 用于预训未见算子时不微调，输入输出作用简单变换，简化后算子求解可靠

这个步骤强制你从"这篇论文做了什么"切换到"一年后的我想知道什么"。

TLDR 应交代**适用场景和核心操作**，而非抽象洞察或论文作者的包装词。
常见形式：什么场景下、遇到什么问题、做了什么操作、达到什么效果。
不总是需要全写；若某部分显然或很容易由其他元素推出，可省略。

可以用自己的概念框架重新框定论文。比如作者用 "constraint-aligned optimization" 来描述，你可以写成 "ansatz 加不训的常数偏置"。同一个方法，完全不同的解读角度。

**TLDR 不是对作者摘要的压缩。** 用你自己的语言和术语来描述。
检验：忘掉论文内容后重读 TLDR，每个词是否需要回忆论文才能理解？
如果需要，"OOD""regime"等论文框架词就不该出现，换掉。

典型结构举例：
```
场景描述（压缩到最简），核心操作（同理）
NO 架构，单层内同时用频域、原空间域信息交互

问题诊断，解决方法
PINN 难训归因…；解决，ansatz 加不训的常数偏置…

数据集描述，关键特性
自行车设计数据集，40 约束、10 目标
```

怎么写：
- **一个语义节点，一个物理行**。每个 TLDR、主 bullet、子 bullet 都必须在源文件的单一物理行内完整结束
  - 笔记 Markdown 按 Tab 大纲解析，换行永远创建另一节点，不能用于同一节点的排版或续句
  - 内容过长时，先压缩、删减或重写。若确有多个独立信息点，可拆成多个节点：每个节点分别表达完整判断，而非让新节点补足前一节点未完成的语法、对象或论断
  - 检验：单独折叠全部子节点后，父节点仍是完整表达；若子节点只是父节点的续句，则必须合并、压缩或改写
- **凝练判断词**："难训"优于"存在梯度冲突"，"不训"优于"不由BP训练"

#### 骨架 bullet

1. **设计 TLDR**：一句话讲完整故事（问题诊断 + 解决方法）
2. **设计骨架 bullet**：核心洞察及其主要支撑论点，每个一行
3. **为骨架 bullet 填子 bullet**：细化、举例、佐证（不得把同一信息点拆成父节点和续写它的子节点）

设计骨架 bullet 时，遵循以下行首与层级规则（子 bullet 同样适用）：

**行首提示查阅时机。** 各 bullet 行首通常应标注"读者在什么情况下值得读这一行"，即检索入口。
- 设想未来遇到什么问题时，会想起这篇论文、回来查笔记。在行开头写出相应回查线索，使后半行成为其具体展开
- 如"推理方式：边解码左右态，再经 Rusanov 更新 cell"
- 常用检索入口类型（取决于读者未来最可能带着什么问题来查）：
  - 讨论对象：如"推理""训练""架构""数据"——读者想定位某个层面时
  - 目的/问题：如"降数据量""保等变性"——读者想解决某个问题、达到某个目标时
  - 现象归因：如"OoD 失败机制""难训归因"——读者遇到失败或异常现象时，回来查原因与对策
  - 可多类组合：如"架构—保等变性""训练—降数据需求"
- 常见错误警示：行首不是内容总结，也不是地位/关系解释。避免以下反例：
  - 内容总结式：单独"归纳偏置""中心化"只是复述这行讲什么，读者不会带着具体技巧名来查
  - 地位/结构宣称式："论文定位""关键设计""主要发现""第 N 贡献"（括号包裹如"（第二贡献）"亦同），只宣称重要或交代论文结构，不帮助判断能否回答当前回查问题
- 公式、引文、紧跟父行的限定或短续句，若没有自然的回查线索，不必硬加
- 检验：设想读者带着一个问题回来，只看行首，是否足以判断"这里能否回答我的问题"？不能则重写

**父子层次结构。** 设计完所有骨架 bullet 后，逐对检查：它们之间是并列关系（各自讨论独立维度），还是从属关系（一个讨论整体框架，另一个是该框架的子组件/子维度）？
- 若为从属，将子概念缩进到父概念下，不要留在同级
- 若为从属，再检查父 bullet 是否显露了子树会回答的问题；不能等到展开后才知道下面有当前所需的信息

**预判读者的理解路径。** 笔记只给未来的自己看。写每一行时，推演那个忘记细节的你读到这里的认知状态：这行能立刻理解吗？会触发什么疑问？下一行是否解答了它？
写完一段后逐行重读，哪里卡住了就调整，不是最后再做，而是在写的当下就做。

这首先是一个推演习惯，其次才体现为一些常见的写法选择（不穷举，关键在习惯）：

- **模糊指代后紧跟消歧。** 不是只说"两阶段"，补充成"两阶段（全局+块状局部）"让读者无需带着"哪两个"的疑问继续往下。如果当前行太长放不下，消歧内容尽量在紧邻位置出现。
- **前提在问题之前。** 先交代"L 只修部分块以降计算量"，再让"选哪些块"自然涌现。先问"选哪些块"会让不理解前提的读者困惑。
- **当前层自解释。** 每层信息读完后最好让读者立即理解，不依赖下层来解码。
  - 如讨论"选块"方式，说"routing score"不自解释（它是间接手段，需要下层解释才能知道它在衡量什么），而其直接手段"依据时间更新幅度"读了就懂。
- **每行开头尽量提示查阅时机。** 写每一行（含子 bullet）都遵循上文「行首提示查阅时机」规则：先想读者什么情况下需要这行，把检索词放开头。
  - 检验：把行首当检索词，读者带着问题回来时，只看行开头能否判断该继续读还是跳过？
- **父 bullet 提示子树能回答什么。** 有子层时，父 bullet 先给出子树共同的判断或问题范围，不能只作分类标签。
  - 检验：若答案藏在某个子层，带着该问题读父 bullet 时，能否意识到应展开它？

### 3.4 内容要素

#### 关键数据与标注出处

记录未来重读笔记时可能需要的关键数字（样本量、误差值、加速比）、数据集构成、训练验证测试比例等。

记录关键信息时，如果知道它在论文中的具体位置（公式号、图表号、章节名），应当同时标上。不知道具体位置的不必硬凑。
比如写"PLI 数据集 5293 个仿真，38 通道"，顺手标上数据集描述所在章节"sec4.1"；写某个公式，顺手标上"eqn(15)"。

#### 引文：你的压缩安全网

`> ` 引文格式在以下情况使用：
- 关键定理、公式的精确表述
- 特别精辟、无法更好改写的重要论断
- 需要精确对照原文的实验设置和数据
- 论文对自身方法的定义性描述（未来参考时可能需要查原文）

**引文应翻译成中文。** 引文应精确忠实于原文，不允许随意调整表述，但也需以用户最熟悉的语言呈现。
整段翻译后附上原文出处（如"secX.X"等章节标签），方便未来对照查证。
数学公式和无法自然中译的关键术语保留原文。

**引文是你压缩的安全网。** 当你用极度压缩的语言概括了论文的一个论断后，附上引文。
如果未来的你读不懂你的压缩表述，引文可以帮助你还原上下文。
对于 arXiv 预印本，保留关键引文还可以对照版本更新。

引文的数量由关键论断的数量决定。不要走向另一个极端：如果笔记大多数行都以 `> ` 开头，说明你在摘录而非思考。

正确使用方式：先用自己的话概括，引文在下方作为佐证和对照。不要反过来，先堆引文再试图总结。

#### 评注

你自己的评价、质疑、联想、比较，是笔记最有价值的部分。每篇论文读完都应该有自己的判断。

评注不用 `> ` 前缀（那是摘录翻译原文时用的）；可以用 `* （AI 评）` 显式标记。
只要是你写的对论文的独立判断（如质疑、联想、与笔记的对照），而非原论文内容的转述，都应标记。
例如：与已有工作的比较，除非是论文引用并讨论了对比对象、笔记仅包括对原文的忠实记录，才不标；论文未引，或仅一笔带过而你做了深度展开，都属独立判断，应标记。

**标记作用域。** `（AI 评）` 作用于所在 bullet 及其全部子孙节点，不作用于任何同级节点。
整棵子树都是评注时，只在根节点标记一次；若仅部分子树是评注，则在对应子树根节点单独标记。

**评注应简短聚焦。** 可以分散在笔记各处、与相关内容紧邻，但每个评注要围绕一个点展开一两层细节，不要只是抛一句标签式判断（"这里有点问题""那里也不太对"这读起来像抱怨清单）。
参考 `raw/AISClit8.md` 和 `raw/AISClit9.md` 中的评注写法：通常一两行，最长也不过一个小层次。

**区分归因判断和审美评价。** 归因判断是对论文本质的评判（"这个方法的前提假设是……如果假设不成立就退化""论文声称解决 A 但实际只解决子问题 B"），对未来有用。
审美评价是带情感色彩的褒贬（"拍脑袋""最聪明""比 XX 强"），对未来的你帮助有限。
用归因句式替代审美标签，说清楚"为什么好/不好"，而不是仅仅说"好/不好"。

**区分边界 critique 和根基 critique。**
边界 critique 在论文的因果框架内追问适用条件（"这个方法在 Re 数更高时是否还 work？""如果观测不是均匀随机分布会怎样？"）。
根基 critique 挑战论文自己的因果诊断（"论文说 L2 对高频惩罚不足导致过平滑，但我认为 L2 实际是过度惩罚了高频""这篇论文对问题的诊断可能不对，真正的原因其实是……"）。
两种 critique 都有价值，但根基 critique 是更高层次的对话，它不只是在方法的边界上划线，而是在论文的因果链上找断裂点。
每篇笔记中，至少尝试问一次：论文对问题的诊断是否可能有误？

评注举例：
- "论文声称解决了 A 问题，但实际上它的方法只解决了 A 的一个子问题 B" ← 挑战论文的声称
- "论文说 X 是原因，但我认为真正的原因是 Y" ← 提出替代因果链
- "这个方法的本质就是把 X 和 Y 解耦，这在 Z 领域其实是一个标准做法" ← 跨领域联想
- "这个方法的前提假设是……如果假设不成立，方法就退化为……" ← 边界条件分析
- "如果是我做，我会……"或者"有没有更简单的方法达到同样的效果？" ← 替代方案思考

#### 重新框定：用你自己的框架重写

不要满足于用自己的话重组论文内容。更进一步：尝试用一个与论文不同的概念框架来重新解读方法。

**为什么需要重新框定。** 论文有自己的框架（如 CAML 用 "constraint-aligned optimization" 来呈现 c-offset）。这个框架是作者选来包装他们工作的，不代表它是最有洞察力的框架。
换一个框架（如 "ansatz design"，把 c 看作不由 BP 训练的手工偏置）可能暴露论文没意识到的联系、揭示方法更简单的本质、或暴露框架本身隐含的局限。

**重新框定的方法。**
- 从相邻领域借框架：这个方法在另一个领域叫什么？被归类为什么范式？
- 追问本质：去掉所有名词包装，这个方法在做什么？它最像哪个已有技术？
- 追溯归属：这个设计选择如果换一个领域背景，属于什么已有范式？

**标注对应关系。** 重新框定之后，附上你的框架与作者框架的对应关系。这有两个作用。
一是未来的你如果不理解你的框定，可以通过对应关系追溯到原文。
二是当两个框架有分歧时，分歧点本身就是有价值的诊断，往往揭示了两种框架对问题本质的不同理解。

**不需要每篇论文都做完整重新框定。** 但如果一个方法让你觉得"这听起来很熟悉但论文用了完全不同的话在说"，那就值得做。
如果无法做到重新框定，至少记录你是从什么角度理解这篇论文的、与作者的角度有什么不同。

#### 比较时拆分正交维度

比较两个方法或设定时，不要写成"A 做了 X 和 Y，B 做了 X' 和 Y'"的并列表述。
先识别独立差异维度（通常 2–3 个），每个维度单独一行说明两方做法。
检验：两个维度能否自由交叉组合？能，就是正交的，应分开讨论。
仅一个实质差异时不必拆分。

### 3.5 写作风格

#### 极致压缩

每句话都要承载信息量。删掉过渡词、修饰词、背景介绍、已知基础知识。

**风格定位**：你不是在写审稿意见，也不是在写公众号文章。你是在给自己发消息，用最直觉的表达、最粗暴的缩写、甚至不完整的句子。怎么快怎么来，怎么直觉怎么写。

**用断续的短句，不要写流畅的解释段落。** 每一层缩进是一个独立的洞察，不是一个段落的组成部分。笔记读起来应该像"子弹笔记"（bullet journal），不是散文。

**每个 bullet 表达一个独立洞察，不写多句段落。** 避免教程式的渐进展开，直接说结论，不要从背景铺垫开始。
笔记的信息密度应该高于论文，而非低于它。
如果一个 bullet 读起来像一句完整的解释性散文，拆开或压缩。

**用口语化、甚至粗暴的缩写。** 你不是在发表论文，你是在给自己写速记。举例：
- "训不动"、"难训" 优于 "训练困难"、"存在梯度冲突"
- "不训" 优于 "不由 BP 训练"、"不参与反向传播"
- "归因" 优于 "根本问题"、"问题根因"

如果某个词删掉后不影响理解，就删掉它。如果整句话都可以删掉，就删掉整句话。

**压缩时警惕歧义。** 压缩常把双字词压成单字，单字可能多义（如"如"可作"例如/如果"、"加"可作"并列叠加/数值加法"），句子里两种都说得通，回看时产生误会。
- 有歧义时优先换无歧义表述：换特殊符号（并列"加"→"&"）、换更精确的单字（"如"→"例"表例如、"若"表如果）
- 找不到合适的替换单字时，才补回双字词（如"叠加""相加""例如""如果"）

#### 归因判断而非解释

如果你发现自己写了"这背后的原因是……""其本质在于……"这类解释性引导语，删掉它们，直接说结论。
更进一步：用归因句式下判断，不用描述句式做解释。前者是你在自言自语下判断，后者是你在给读者解释。
- "PINN 难训归因：PDE non-uniqueness → 参数空间扭曲 loss valley"（归因）
- "问题根源在于 PDE 算子的非唯一性导致参数空间中出现扭曲的损失谷地"（描述）

**警惕元概括。** "这本质上是……""核心贡献不是 X 而是 Y""论文揭示了一个机制：……"这些句子的功能是告诉你自己在做概括，但它们不增加任何信息。
直接说本质是什么，不要让"本质"这两个字占用空间。如果正文本身已经体现了某个判断，不需要先用一句话预告这个判断。

**用判断句，不用属性标签。** "预训练不总有益"直接说出结论。"预训练的条件性"只是一个分类标签，读者需要自己翻译"条件性到底意味着什么"。笔记要的是判断，不是分类学。

#### 概念处理

**不要解释已知概念。** 作为领域专家，你已经知道 FNO 是什么、知道 PINN 是什么、知道注意力机制是什么。
如果你发现自己写了"FNO（Fourier Neural Operator，一种基于傅里叶变换的……）"，删掉括号里的内容。

**论文特有概念机制要解释。** 像 anchor loss 定义、TTT 流程、本文新定义的概念、"cell"的具体含义，这些不是领域常识，一句话交代清楚，放在首次出现的位置。

**给论文一个概念定位。** 这篇论文在整个领域中处于什么位置？它是一个新的基础模型，还是对已有架构的改进？它是一个 benchmark 论文，还是一个方法论贡献。
用一句话在笔记早期给出这个定位，帮未来的你快速理解这篇论文的"身份"。

**不要和论文自己的 limitations 段落抢话说。** 如果论文明确列了自己的局限（"only steady-state""no theoretical convergence guarantee"），不需要你在笔记中复述。
但如果你有论文没提到的局限，或者你不同意论文对某个局限的评估，那才是值得记录的内容。

#### 取舍指南：你不是在写参考文档

如果有人需要了解论文的全部内容，他们应该去读论文。你的笔记只应该包含你从论文中提取出来的、对你有价值的东西。以下内容通常可以省略：

- **常规的实验结果**：除非实验设计本身有巧思（如巧妙的基准构造、新颖的评估指标、反直觉的发现），否则不用写"在 X 个数据集上超越了 Y 个 baseline"这类常规结果。
  - 不要按 RQ1/RQ2 逐一列举实验结论，不记具体误差数字。
  - 但消融所揭示的"哪个组件解决哪个问题"的归因关系如果有助于理解方法机制，可以一两句概括。
- **方法的技术细节**：省略网络层数、学习率、超参数等常规实现细节。但如果方法的核心创新就体现在某个具体的数学公式或计算过程中（如注意力分数的计算方式、投影算子的形式、网格初始化公式），这些不是"细节"而是方法的本质，保留。
- **区分方法的"常规细节"和"独特要点"**：网络超参数是方法细节（省略），但论文给出的数据处理管线、实验测量数据的预处理步骤（如 DIC 位移场到网格节点的插值流程、可靠性判定准则）若是本文独有、其他论文所不会涉及的要点，应予记录。未来如果你需要复现或借鉴这个流程，这些信息比方法公式更难从论文中快速定位。
- **论文的背景和动机**：读者（未来的你）已经知道这个领域为什么重要。

## 4. 笔记格式

### 4.1 文件结构

```markdown
* 方法名-arXivID 你设计的TLDR
	* "Paper Title in Full", 发表位置简写
		* Author1; Author2; Author3;
		* 核心作者所在机构（优先用简称、缩写，中英文哪个短用哪个）
		> created on YYYY-MM-DD by [软件框架 + 完整模型名]
	* 方法全称：xxx（当方法名存在且为缩写时，应补充此行）
	* 正文内容（按分析逻辑组织，引文和评注穿插其中）
```

- **方法名**：论文的核心方法简称，应来自论文本身使用的简称。不要自造论文中没有的缩写。没有显著方法名的可省略。
- **arXiv ID**：取标识符后段（如 `2604.23098`，不要前面的 `arXiv:`）。即使论文已正式发表，也应记录 arXivID。
- 方法名、arXivID 任一缺失时，省略连字符和对应部分；都缺失则不写。
- **发表位置**：需核实论文是否已正式发表。
  - 已发表的标注会议/期刊简写 + 年份（如 `ICML 2026`、`Nature Communications 2026`）
  - 仅 arXiv 预印本的省略发表位置，只保留 `"Paper Title in Full"`
  - 不确定时主动检索确认
- 作者列表用英文分号分隔
- `created on` 行：AI 生成的笔记需注明软件框架和完整模型名（如 `> created on YYYY-MM-DD by OpenCode + GPT-5.6-Sol-low`，模型名注意大小写）；人类笔记只有日期。不要改动已有的人工笔记
- **方法全称**：仅当首行使用了方法名缩写时加入。若首行中无方法名、或方法名本身已是全称，可省略
- tab 缩进构建层级关系：每深入一层细节增加一级缩进，表示从概括到细节的展开
  - tab 缩进只表示另一条独立的从属信息，不得承担视觉换行、断句或续写功能
- 原文如实精确翻译用 `> `，自己的评注用 `* （AI 评）` 不加 `>`

### 4.2 标点与标记

- **避免为术语添加不必要的引号或格式强调。** 不要用引号（""或「」）、粗体（**）、斜体（*）来标记术语，未来的你知道这些词的含义，格式噪音只会降低阅读效率。
  - 引号保留给直接引用原文的场合；但如果引号服务于精确语义（如区分"论文声称的 A"和"实际发生的 A"），可以保留
- **英文术语仅用于中文表达不自然的情形**（如 ansatz、token、patch、softmax）。能用中文的地方一律用中文
- 不要出现"本文""该论文""作者认为"等第三人称表述。你在写笔记，不是在写论文 review。直接用第一人称判断或省略主语
- 正文的层级标题应反映你的分析逻辑，不要以论文的"摘要""引言""方法""实验结果"等章节名作为笔记的组织框架。如果需标注引文来源，可以用章节名作为简短标签，但不作为组织标题

### 4.3 数学符号

数学表达式用行内 LaTeX 公式 `$...$`。不要使用行间公式 `$$...$$`。关键数学表达式优先用符号形式记录，而非纯文字描述。

能用公式精确承载的关系优先用公式，文字留给概念解释。三种情形尤其值得公式化：
- 精确关系（loss、映射、数据配置）文字冗长费解时，公式更简明
- 多个配置并置对比时，公式使差异一眼可见（如监督用 $(u_l^r,u_h^r),(u_l^s,u_h^s)$ 与半监督用 $(u_l^r,u_h^r),(u_l^p,/)$）
- 同一较长公式若多处共享，只写一遍、不重复，其他地方只引述（如两网络用同一 loss 仅反传角色不同）

使用公式前，参与运算的对象先命名，跨行符号统一；前文已定义的符号不重复解释。

写完后分三步检查，必须全部通过才能交付：
1. 定性检查（见下清单）
2. 脚本检查（`scripts/check-note.sh`）
3. 子 agent 第三方审视（不可省略）

### 5.1 定性检查

- [ ] 笔记中出现你自己觉得"读起来不像给自己写"的句子？找出这些句子，逼自己改写
- [ ] 每个信息节点是否只占一个物理行？是否有任何 bullet 写的句子不完整，实际由其他 bullet 在续写？

（其他常见问题如"删掉这一段会丢失核心洞察吗""有解释已知概念吗""有复述论文 story 吗""顶层组织围绕论文章节顺序吗"已在 §1–§3 各处说明，撰写时请即时自检，不在此重复列举。）

| WARN | 行长度 > 100 字符（所有行类型统一） | 专家笔记 90% 行 ≤ 80 字符 |
| WARN | 行长度 > 120 字符（所有行类型统一） | 极少出现在专家笔记中 |

**额外自查**：脚本末尾会提示建议自行 grep 的模式，你也可以根据笔记内容自行添加。以下是你应该主动想到的额外检查方向：

- 括号解释已知概念（如 `FNO（Fourier Neural Operator，一种...）`）
- 描述句式替代归因句式（如 `其原因是...``问题根源在于...`）
- 英文半角标点混入中文正文（排除 LaTeX 公式内的标点）

做完所有检查和修改后，重新运行 `scripts/check-note.sh "$FILE"` 确认无 FAIL 项。

### 5.3 第三方审视

定性检查和脚本检查全部通过后，并行启动两个拥有全新上下文、无需编辑权限的子 agent（告知笔记文档的完整路径），从不同角度审视笔记。
两者全部完成后，综合所有反馈判断是否修改。

**A. 未来读者盲审（不加载 note-writing skill）**

子 agent 启动后先读取盲审要求 `references/blind-review-guide.md`（位于本 skill 目录下）
了解审视方法论与报告方式，再对笔记执行审视。
需告知子 agent 盲审要求文档的完整路径、待审笔记的完整路径。

**B. 写作准则审视（加载 note-writing skill）**

加载本 skill（给完整路径），以 skill 中的写作原则为透镜审视笔记。
重点关注脚本无法检查的思想质量维度。

### 5.4 修订循环

若综合反馈后进行了大规模重写（不是局部微调），需要从头进行三步检查，包括重新启动两个有全新上下文的子 agent 审视重写后的版本。
- 总共最多 3 轮审视（初次 + 2 轮重审），即 3×2 = 6 个子 agent
- 第 3 轮审视后不论结果如何都不再启动新一轮，即便仍有大改动也直接交付
- 局部微调（如不超过 7 行）不需要重审，直接交付
- 判定"大规模重写"的参考标准：重组了顶层结构、删除或重写了 20% 以上的内容、改变了核心洞察的表述层次
